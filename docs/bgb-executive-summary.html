2. How to Avoid the "Predicted values must be in range [0, 1]" Portal Error

Earlier runs across the GEMSDOE family suffered submission rejections with the portal message Error: Predicted values must be in range [0, 1] when exporting GeoTIFFs that contained NaN outside the study footprint, negative sentinel values (-9999.0 or -3.4e38), or unclipped tree logits. The shared writer (vendor/gems57/submission_writer.py) and preflight validator (scripts/validate_submission.py) prevent this class of error by enforcing six invariants on the primary -zeros.tif artifact:

  1. Write 0.0 (never NaN or -9999) outside the active footprint and set nodata=None in the GeoTIFF profile so strict array validators that run (arr >= 0.0) & (arr <= 1.0) across the full 3730×3292 array evaluate to True on all 12,279,160 pixels.
  2. Clip and binarize predictions inside the footprint to exact float32 values in [0.0, 1.0] (specifically 0.0 and 1.0 for discrete dot covers).
  3. Zero out all mapped catalogue fault pixels (existing_faults.tif == 1) plus a 300 m (3.0 px) exclusion collar so zero false-positive budget is wasted near known faults that the organizer masks during scoring.
  4. Match the exact reference grid of sample_submission.tif: CRS EPSG:32611, dimensions 3730 rows × 3292 columns, affine transform (100.0, 0.0, 243350.0, 0.0, -100.0, 4508550.0), single band, DEFLATE compression.
  5. Package a single-member .zip archive containing only the .tif at root level for portals that prefer zipped uploads.
  6. Keep the submission note $\le 140$ characters (138 characters for H77-BGB):
    H77-BGB basement growth-wedge + transtensional strain + clay-cap breach (37654 dots); HOLDOUT-DTI 0.0584 lane / 0.1024 LOCO; DO NOT UPLOAD
