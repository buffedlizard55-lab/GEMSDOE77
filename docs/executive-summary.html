Why the "Predicted values must be in range [0, 1]" error will not recur

The problem description asks for one float32 band with values in [0, 1] inside the study area. The earlier rejected files most likely had NaN or nodata-tagged cells inside the scored area, which the portal reports as out of range. This cause is our reading of the evidence and has not been confirmed by the organizer (irregularity I09). The -zeros files avoid this: every one of the 12,279,160 cells is finite and exactly 0.0 or 1.0, there is no nodata tag, and the grid is copied from sample_submission.tif. This is the encoding of the GEMSDOE32 file that the owner reports scored 0.2778. Each file is read back and passes 17 checks against the official footprint (src/gems77lia/validate.py). The shared template validator is also run. It reports only its known mismatch: it derives the footprint from a feature band, which differs from sample_submission.tif by 4,601 cells. The -nan twins (NaN outside the study area) are kept for reference only; upload the -zeros file.
