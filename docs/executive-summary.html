The portal error “Predicted values must be in range [0, 1]” — root causes & the permanent fix

Two distinct defects produce this message, both measured in this data family:

  • Float sentinel written through: training_features.tif uses nodata -3.4028234663852886e+38; thousands of such cells lie inside the footprint. Any pipeline that copies them into a prediction emits values far outside [0, 1].
  • Nodata-tag / NaN-outside fragility: files carrying a nodata tag outside [0, 1] (or relying on NaN handling) can be rejected by range scanning even when in-footprint values are legal.

Fix used here (shared gems57.submission_writer, fail-closed, no silent repair): the prediction is validated in memory as finite in [0, 1] everywhere, written all-finite with nodata=None (0.0 outside the footprint and on the mapped catalogue), re-read from disk, and re-validated (single-band float32, EPSG:32611, 3730×3292, transform identical to the sample submission) before the ZIP is packed. This session's file additionally passed an independent plain-rasterio re-read: 12,279,160/12,279,160 cells finite, min 0.0, max 1.0, zero NaN — receipt. Local validity is not organizer acceptance; it eliminates the known mechanical causes of the range error.

What “good” looks like at selection time (checklist)

  • Promotion gates all green (paired CI vs controls excludes 0; uniqueness ρ ≤ 0.90 and mutual 3-px overlap ≤ 0.70; writer + independent re-read validation).
  • Full-inventory uniqueness certification (beyond any single repo's local subset) and weekly-cap confirmation by the human selector.
  • Only then: one upload, receipt recorded as ORGANIZER-CONFIRMED.
